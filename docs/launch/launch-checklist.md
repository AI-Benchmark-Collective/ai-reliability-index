# Coordinated launch checklist

Do not begin the broad launch until every release gate is satisfied.

## Release gates

- [ ] Fresh installation succeeds from the public README.
- [ ] A non-maintainer reproduces the alpha locally.
- [ ] CI passes on all supported Python versions.
- [ ] At least one real adapter result set receives independent review.
- [ ] Raw traces or a documented nondisclosure reason accompany every run.
- [ ] Model, framework, prompts, tools, pricing, dates, and retry policy are frozen.
- [ ] Headline numbers match the machine-readable summary.
- [ ] Limitations and conflicts are published beside results.
- [ ] Evaluated vendors receive a factual correction window, not editorial control.
- [ ] Contributor names and authorship are approved by those individuals.

## Coordinated release day

1. Publish the versioned GitHub release and immutable result artifacts.
2. Publish one canonical technical report.
3. Notify contributors with individualized attribution links.
4. Submit a runnable demonstration to Hacker News only if users can try it.
5. Publish technical threads on LinkedIn and X from the project account.
6. Email relevant researchers, newsletters, and evaluated providers.
7. Monitor questions and corrections for the next 12 hours.
8. Record referral traffic, clones, runs, issues, and pull requests.

## Headline standard

Use the strongest result that survives reproduction. State the sample size and scope.
Never generalize from one task family to all professional work.
